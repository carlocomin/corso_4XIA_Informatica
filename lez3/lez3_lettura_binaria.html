Leggere e controllare un file binario

Prima ricostruisci il contratto; poi accetta i dati soltanto se il file lo rispetta interamente.

← Precedente Successiva →

Non fidarti dei dati appena letti

Idea chiave: verifica prima la riuscita dell’operazione, poi il significato dei campi. Solo dopo questi controlli usa n per determinare quanti byte leggere nell’array.

I controlli hanno un ordine

  1. Apertura riuscita e header letto completamente.
  2. Magic e versione riconosciute; n <= MAX.
  3. Ricevuti tutti gli n × 4 byte dei valori.
  4. Nessun byte extra e nessun errore di I/O.
  5. Solo ora: elaborazione dei valori.

Prima segui un caso riuscito: 10, 20, 30

  1. Header: ci aspettiamo ARRB, versione 1 e n = 3. memcmp confronta i quattro byte dell’etichetta.
  2. Array: chiediamo 3 × 4 = 12 byte, non tutta la capacità dell’array.
  3. Risultato: se il file è completo e non contiene dati extra, stampiamo 10 20 30.

Segui prima questo percorso. Poi proveremo i controlli su un file sbagliato, un errore alla volta.

Fine file attesa o file troncato?

Mancano dati necessari: errore

Servono 12 byte di valori e ne arrivano soltanto 10. Il file è troncato: read fallisce e non elaboriamo l’array incompleto.

Abbiamo tutto: fine corretta

Abbiamo letto header e n valori. Cerchiamo un altro byte con get(extra): se non c’è perché il file è finito, va bene. Se c’è, il formato non è rispettato.

Da ricordare: “mancano byte necessari” è un errore; “non ci sono byte dopo il contenuto previsto” è la fine corretta.

Mostra dettagli dei controlliNascondi dettagli

gcount() indica quanti byte ha trasferito l’ultima lettura non formattata: aiuta a spiegare perché il blocco è incompleto.

Leggere esattamente l’ultimo byte non obbliga lo stream a segnalare subito EOF. La lettura di prova lo distingue da dati extra. Dopo questa prova controlliamo bad() e eof(), non soltanto !in, perché il tentativo a EOF è atteso.

Checkpoint

L’header dichiara 3 valori, ma l’ultimo ha soltanto 2 byte: possiamo usare i primi due valori?

Mostra rispostaNascondi risposta

In questo contratto no: il file è incompleto e si rifiuta l’intero caricamento. Un trasferimento parziale può anche avere modificato una parte dell’array: il codice non lo elabora dopo il fallimento.

Esercizio 13bis

Collauda senza ricreare il file

Base: esegui lo scrittore e poi il lettore; verifica 10 20 30. Controllo guidato con il docente: crea una copia del file corretto di 24 byte e modifica una sola cosa per volta con un editor esadecimale. Prova separatamente: togli l’ultimo byte; aggiungi un byte; cambia la magic; usa un file con header valido e n = 0. Esegui soltanto il lettore dopo ogni modifica, non lo scrittore.

Mostra soluzioneNascondi soluzione

Nel caso base si stampano i tre valori salvati: 10 20 30. Per i test guidati:

  • 23 byte: blocco incompleto, gcount() = 11 sui 12 richiesti.
  • 25 byte: errore per byte aggiuntivi.
  • Magic diversa: formato rifiutato prima dell’array.
  • n = 0: valido soltanto se il file ha i soli 12 byte di header; nessun valore stampato.

Se eseguissi di nuovo lo scrittore, cancelleresti la modifica da collaudare.
